# 决策：worker 汇报从「推进主管终端」改为「落收件箱、主管拉取」

**日期**: 2026-09-19
**状态**: 提案中（user 2026-09-19 口头认可方向："欧卡的这个方式比我们好多了"，待正式拍板 → 见 open-questions Q24）
**关联**: plan.md → 待立 milestone（派单 / 汇报通道重构）
**来源**: 2026-09-19 实测对比：PM 通过 Orca 派 codex 代码工程师同步 GitHub，全程未被打断；同日 user 反馈 hive 现有 `team report` 注入模式会打断输入

## 背景

hive 现在的汇报链路：worker 做完跑 `team report` → runtime 写 dispatch 账本、tasks.md 自动打勾、Cockpit 亮灯 → **同时把汇报文字注入主管 PTY 的标准输入**。前半段（账本 / tasks.md / Cockpit）是对的，问题出在最后一步：注入等于有人在 user 打字打到一半时往输入框里粘贴一段话。user 原话："不会打断我的输入，这样的话感觉好多了。"

同日在 Orca 里派 codex 做同一类任务，体验完全不同：
- PM 把任务文字发进 codex 终端（等价于替 user 敲一段话回车）；
- codex 只在自己终端里干活，输出一个字都不进 PM 输入框；
- PM 在后台每 6 秒查一次 git 状态（新提交 / 工作区干净 / 与远端零差异），三条件满足即完成；
- Orca 自带的协作通道也是同一思路：worker 用 `orca orchestration send` 投消息进收件箱，协调者 `orca orchestration check` 主动取，**消息永远不碰终端输入**。

本质区别一句话：**hive 是推（push），Orca 是拉（pull）**。

## 决策

1. **worker 汇报只落账本，不再注入主管 PTY。** `team report` 保留，行为改为：写 dispatch 账本 + tasks.md 打勾 + Cockpit 亮灯 + 标记"待主管读"，到此为止。
2. **主管在"下一轮开口前"拉取。** 用 Claude Code 的 UserPromptSubmit 钩子（codex / 其他 CLI 找等价机制）：user 按回车发消息时，runtime 把所有"待读汇报"作为背景上下文附在那条消息后面一起送给主管。user 打字过程中永远不被插话，主管每次开口前必先读完所有汇报，不会漏。
3. **保留空闲兜底，但加"user 未在输入"条件。** 主管空闲超过阈值 **且** 前端上报 user 输入框为空、无焦点活动时，才允许注入一次。目的：user 长时间离开时，review / commit 不会无限延后。
4. **完成信号优先取客观状态，不取 worker 自述。** 凡是任务有可机器判断的终态（git 干净 / 文件出现 / 测试通过 / 账本某行 done），主管以该状态为准，worker 的文字汇报只作补充说明。

## 理由

1. **不打断人是硬需求。** user 明确反馈；PM 体系"人 CEO + AI COO"的前提是 AI 不给人添堵。
2. **拉模式不丢信息。** 汇报仍完整落账本，Cockpit 实时可见；主管拉取时一次读完，比逐条注入更完整。
3. **改动面小。** 账本 / tasks.md / Cockpit 这三层基础设施已存在，只改最后一步的投递方式，不动 worker 侧命令。
4. **与已有"非 busy 时 timeout 兜底投递"（169056c）兼容。** 那条修复解决的是"汇报静默丢失"，本决策把它收窄成"空闲且 user 未输入时才投"，不是推翻。

## 已知代价

- **延迟。** user 很久不发消息，主管就很久不知道 worker 完了；靠第 3 条兜底缓解，但兜底阈值内的等待是真实代价。
- **失败信号也变慢。** 推模式下 worker 报错立刻传到主管；拉模式下同样要等下一轮或兜底。缓解：失败 / 阻塞类汇报 Cockpit 红条 + 手机 push，走 user 而不是走主管终端。
- **需要前端配合上报"user 是否在输入"。** 没有这个信号，兜底注入仍可能撞上打字；这是新增的一个前后端接口。
- **codex / gemini / opencode 作主管时的钩子机制各不相同**，第 2 条要按 CLI 分别落地，短期可能只覆盖 claude 主管。
