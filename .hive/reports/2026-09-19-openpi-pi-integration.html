OpenPI × Pi：它们如何配合

OpenPI 不是另一个需要和 Pi 对接的 Agent 服务。它是一个 Pi Package，直接加载到 Pi Coding Agent 内部，用 Pi 的 Extension API、Session、Provider、模型、Skills 与 Trust 边界增加多代理、Workflow、后台进程和本地 Web 工作台。

结论：你当前机器可以直接安装。现有 Pi 为 0.85.1，OpenPI 最新 npm 版为 0.8.1，最低要求正是 Pi 0.85.1、Node 22.19+；本机 Node 为 25.5.0，且 pi list 显示尚未安装其他 package。推荐先用 npm 稳定版安装，保持默认 explicit 能力发现，完成四项 smoke 后再决定是否开启 adaptive。

二、代码里实际怎样接上 Pi

Package 声明

package.json 的 pi.extensions = ["./extensions"] 让 Pi 原生 package loader 载入扩展目录。OpenPI 把 Pi 的 pi-ai、pi-coding-agent、pi-tui 声明为 peer dependencies，不复制一套核心运行时。

能力按需加载

before_agent_start 钩子分析用户意图；明确说“用子代理”“workflow”“后台运行”等时，才打开对应工具组。默认 explicit，可用 /openpi-setup 改为 adaptive。

Subagent

通过 Pi SDK 的 createAgentSession() 创建进程内独立 Session。它继承允许委派的工具、Skills 与项目说明；不会递归得到父级编排、交互或状态工具。

Workflow

Workflow 的控制脚本在受限 sandbox 中运行，使用 agent()、pipeline()、parallel() 调起 Pi Child Session，并保存 ledger、handoff、artifact 与运行图。

后台终端

OpenPI 管理长期子进程、日志、超时和进程树清理；完成结果通过 Pi 的消息机制进入 Session，不需要把 dev server 卡在主 Agent 的 Bash 调用里。

Web 工作台

/web 或 openpi web 启动独立本地 Web runtime，默认绑定 127.0.0.1。Web 会话与当前终端 Pi 会话相互独立，不会接管终端对话。

三、推荐落地方式

建议从 npm 稳定版开始，因为 GitHub main 可能领先已发布制品，README 也明确提醒二者的运行资产不同。

# 1. 已核对：本机目前满足要求
pi --version        # 0.85.1
node --version      # v25.5.0
pi list             # No packages installed.

# 2. 安装稳定版
pi install npm:@tt-a1i/openpi

# 3. 核对唯一加载来源
pi list

# 4. 进入 Pi 后重载
/reload

# 5. 保持默认 explicit，查看/配置 OpenPI
/openpi-setup

第一次 smoke 建议依次验证：

  1. 普通 Pi：让它读一个文件并做一次普通修改，确认原生路径未被改变。
  2. 后台：“在后台运行 dev server”，再用 /ps 看状态和日志并停止。
  3. 子代理：“用子代理分别检查 API 和测试，最后汇总”，再用 /subagents 查看。
  4. Web：输入 /web，确认只绑定本机地址，创建独立 Web 会话。

五、与 hive-serva 的关系

OpenPI 最适合作为 Pi 这个 CLI 自身的能力层。如果未来把 Pi 加成 hive-serva 的 worker preset，链路应是：

hive-serva（跨进程团队、账本、Cockpit、手机远控）
  └─ Pi worker（顶层 CLI Session）
       └─ OpenPI（Pi 内部的子代理 / Workflow / 后台进程）

两层不要混成同一个调度器：hive 管顶层 worker、持久 dispatch 与人机协作；OpenPI 管单个 Pi worker 内部的短期并发和执行细节。OpenPI Child 不应直接冒充 hive worker，也不应把 OpenPI 的完成态当作 hive 的最终 accept 证据；最终仍应由 hive 的 ledger、测试结果和 reviewer 闸门收口。

六、风险与边界

权限边界：Pi 官方明确说明，它默认没有内建的文件系统、进程、网络或凭据权限沙箱，使用启动 Pi 的系统用户权限。OpenPI 的工具白名单、Workflow sandbox 和 worktree 解决的是能力面与隔离问题，不等同于完整系统沙箱。处理不可信仓库时仍应使用容器或更强隔离。
  • 当前 Pi 恰好在最低兼容版本；可先用，升级 Pi 时要重新 smoke package。
  • adaptive 会允许模型自主加载能力，建议熟悉默认 explicit 后再开启。
  • Web 默认 loopback 安全边界较清晰；若未来转发端口，应额外设置 token 和 origin，不要直接暴露。
  • GitHub main 与 npm 发布物可能不同；稳定使用选 npm，开发/贡献才绑定本地 checkout。

七、建议决策

建议采纳：先把 OpenPI 作为 Pi package 安装到当前用户环境，保持默认 explicit，做四项 smoke；暂不改 hive-serva。等确认 Pi + OpenPI 的实际体验后，再单独评估“Pi 作为 hive worker preset”，避免一次同时引入 package 层与团队调度层两个变量。
