HippoTeam (hive-serva) vs Orca
协作交互模型与使用体验对比

日期：2026-09-19 ｜ 场景：1 个老板 + 1 个 AI 主管（orchestrator / coordinator）+ N 个 AI worker

前置审计（结论已采信，本次不重复审计代码）：.hive/research/orca-vs-hive-codeaudit-2026-09-14.md、.hive/research/2026-07-03-orca-vs-hippoteam-codeaudit.md、.hive/decisions/draft-2026-09-19-worker-report-pull-not-push.md

Orca 版本：CLI v1.4.205（本地 /Users/huangzongning/development/orca-compare）｜HippoTeam：/Users/huangzongning/development/hive-serva

一句话结论：两边的差别不在"谁功能多"，而在「主管的回合由谁发起」。 HippoTeam 把主管的回合边界交给外部（worker 一 team report，runtime 就把正文粘贴 + 回车塞进主管终端，主管被迫开口）； Orca 把回合边界留给主管自己（worker 的汇报只是落库，主管主动 check --wait 拉）。 这不是"push vs pull"的口号差异，而是老板正在主管终端里打字时，系统会不会替你按下回车的差异。 代价也真实存在：Orca 换来了"零打扰 + 零进度感"，HippoTeam 换来了"高打扰 + 强可见性"。

一、先纠正一个容易记错的细节

原始观察是"hive 的 worker report 会被注入主管终端输入，Orca 的消息只落 inbox、coordinator 主动拉、从不碰终端输入"。前半句完全正确；后半句需要精确化，因为 Orca 确实有一条会写 PTY 的通道，只是它是"指针"而不是"正文"，而且门禁极严：

通道Orca 的行为门禁
正文通道
mailbox / DB		 worker 的 worker_done / escalation / question 只写成 orchestration DB 里的行。主管必须自己 orca orchestration check --wait 才能拿到。 无（默认路径，一个字节都不写终端）
指针通道
PTY write		 写一行文本：You have N orchestration messages. Run `orca orchestration check`. 然后回车。（mailbox-pointer-pty-write.ts / formatter.ts:121） ① 必须 leaf.lastAgentStatus === 'idle' 且"观察到是活的"——主管在 check --wait 里（turn 进行中）时直接 return，不写（mailbox-pointer-delivery.ts:46-49）；
② 有未过滤 waiter（主管正阻塞等全部消息）时批为空、完全不发（mailbox-pointer-eligibility.ts:20-24,47-49）；
③ 已被 waiter 认领的类型从指针批里排除（同一函数）。
这个纠正很重要，因为它把对比从"谁写终端"变成了"谁在什么状态下写终端"。
Orca 的语义是：只有当主管空闲地坐在提示符前，才用一行指针提醒它去拉；主管一旦在干活（turn 中），任何东西都不许打断它。
HippoTeam 的语义是：只要主管的 PTY 出现了新提示符（"看起来在等输入"），就把整份汇报粘贴进去并按回车。
两者面对的危险窗口是同一个（主管停在提示符上 + 人正在打字）。Orca 用"状态门禁 + 只写一行指针"把窗口压到很窄；HippoTeam 没有任何门禁，直接写正文 + 回车。

二、两侧定位

HippoTeam（hive-serva）

一个 workspace 目录 + 每角色一个真 CLI 进程（Claude Code / Codex / OpenCode / Gemini）的多 agent 治理工作台。主管是 AI，治理规则写成 L1 代码（角色 ACL、accept gate、反自审校验）与 L2 提示词（hive-team-guidance.ts 的 17 条 ORCHESTRATOR_RULES）。PM 文档体系（plan / tasks / open-questions / decisions / research / reports / baseline）是它的第二张脸。

治理强可见性强打扰强默认不隔离

Orca

以 worktree 为一等公民的并行开发 IDE。主管（coordinator）也是一个真 CLI agent，靠 orca orchestration 一套动词编排：Task DAG、Dispatch、Run、decision gate、blocking ask、阻塞拉取。调度正确性由生命周期状态机 + mutation receipt 保证，而不是靠提示词。

编排正确性强打扰极低worktree 隔离治理无强制

三、六维度总表

维度 HippoTeam 做法 Orca 做法 体感差异（老板视角）
① 派单 主管 team send "<worker-name>" "<task>"（按 name）。runtime 建 dispatch 行、写 tasks.md、把带 dispatch_id 的整段派单正文粘贴进 worker PTY + 回车。 worker-start --spec "..." --worktree current --agent codex 一步建 Task + attempt + 终端 + 提示词注入；或 task-create --deps 先铺 DAG 再 worker-start --task。派单正文同样注入 worker PTY，但终端由 Orca 拥有并监督。 两边都是"注入终端"。差别在 Orca 派单前先落 Task 行（有 id、有依赖、有 outcome），HippoTeam 派单只落 dispatch 行。Orca 派单更"可追踪"，HippoTeam 派单更"随手"。
② 汇报回流 push。team report → 落 ledger + 写 tasks.md + 手机 push + 无条件把 [Hive 系统消息：来自 @X 的汇报] 粘贴进主管终端并按回车。主管的回合边界由 worker 决定。 pull。worker_done → 落 DB。主管阻塞在 check --wait 上等，拿到 FIFO 批（≤50 条）后必须 --ack <delivery_id> 才推进游标（未 ack 会重放同批）。空等待/超时是"检查点"，不是失败。 这是最大的体感分水岭。HippoTeam：老板在主管窗口里打一半字，报告插进来 + 自动回车，老板的字被顶走/被提交。Orca：老板打字时主管若在 turn 中，一个字节都不会写进来。
③ 老板可见性 Topbar Cockpit 按钮带数字徽标（待办 AI action 数）→ 点开 12 个 tab 的抽屉：plan / tasks / questions / ideas / decisions / research / reports / timeline / baseline / archive / setup / diagnostics，每 tab 自带徽标。左侧 worker 卡片显示三态 + 队列徽标。待拍板落 .hive/open-questions.md（Questions tab）。另有飞书 / 手机 App 远程通道 + 高风险动作手机审批。 侧边栏每个 worktree 下的 agent row，row 主文案 = 该 worker 当前 Task 的标题；Agent Dashboard 有 Needs You / Working / Done / Idle 四桶计数；orca worktree ps 命令行能看 live / pty / unread + 终端预览。没有 tasks 面板，也没有 decision gate 的 UI（gate 只存在 orchestration DB 里）。 HippoTeam 是"结构化看板"：内容持久、可回溯、有优先级。Orca 是"实时仪表"：一眼看到谁在忙、谁卡住、哪条 worktree 有未读，但关掉终端后信息就没了。
④ 完成信号 worker 自报 team report 为主。客观侧证：dispatch ledger 8 态（含 report_overdue / orphaned）、tasks.md [x]/[~]、review_status 旁挂、以及 unreviewed-code-status.ts 的"未审代码"看板兜底（coder report 后 2 分钟宽限内无 reviewer dispatch → 硬亮）。 worker 自报 worker_done --outcome succeeded|failed，但状态机自动 settle，且明令"不许再补 task-update --status completed"。铁律："Absence never authorizes stop, abandon, retry, or release"——只有 exited liveness / worker 自证进程退出 / 最后一轮没发 worker_done 才算正证据；unverifiable 只是"不知道"，必须继续等。turn 结束前 worker-list --terminal-state reclaimable 必须为空。 Orca 把"不许把不知道当成已完成/已停止"写成了 CLI 级的纪律，并直接吐出下一步 argv（projection.nextAction）。HippoTeam 有兜底看板，但"报告即完成"的默认路径仍然偏向相信自报。
⑤ 隔离与并行 默认不隔离。一个 workspace = 一个目录，N 个 worker PTY 共享同一个 cwd；worktree 分层要 HIVE_WORKER_WORKTREES=1 才开。写冲突靠角色约定消化：worker 不 commit，PM 审完在主树 commit。并行度 = PTY 数。 worktree 是一等公民。默认 --worktree current，可 new-child / new-top-level，可落 SSH / WSL / 远端 Orca server。每个 worker 一份独立 checkout + 独立分支。并行度 = worktree 数，物理隔离。 HippoTeam 并行靠"约定"，一旦两个 worker 碰同一文件就只能靠人眼发现；Orca 并行靠"文件系统"，冲突变成 git merge 的常规问题。
⑥ 治理 L1 代码强制。角色 ACL（只有 orchestrator 能 send/cancel/accept，worker 只有 report/status）；team accept 必须引用 reviewer 的 dispatch_id 且过三重时序校验（详见下）；sentinel 独立角色；高风险动作（rm / git push / drop table）经手机审批。 无 review 铁律。有的是编排纪律：生命周期 8 态 + mutation receipt + 失败不许盲目 relaunch（要读 failedStage / residualResources）+ "review-only 的 worker_done 只授权综合、不授权 coordinator 改文件" + nested worker 深度限制。 Orca 管"调度没做错"，HippoTeam 管"结论可信"。Orca 里"这行代码谁审过"没有任何记录，全靠主管自觉——这是它最大的一处空白。

四、逐维度展开

① 派单：都是注入 PTY，但 Orca 先落 Task

怎么做

  • HippoTeam：主管跑 team send "<worker-name>" "<task>"。runtime 建 dispatch 行 → 写 .hive/tasks.md → writeSendPrompt → buildWorkerDispatchPayload 拼出 [Hive 系统消息：来自 @<orch> 的派单] + 角色 + "你必须遵守" + dispatch_id + 任务正文 + PM_DISPATCH_REMINDER + worker capability manifest + Cockpit 快照 + <hive-system-reminder> 尾，整段粘贴进 worker PTY。
  • Orca：worker-start --spec "..." --worktree current --agent codex --json 一次调用同时创建 Task、attempt、终端、注入提示词，并接管资源所有权；复杂依赖先 task-create --deps '[...]' 铺 DAG，再用 task-list --ready 当"外部记忆"。dispatch --inject 是逃生口，被明确标注为"unmanaged"。

老板看到

  • HippoTeam：左侧 worker 卡片队列徽标 +1；Cockpit tasks tab 多一行 - [ ]。
  • Orca：侧边栏对应 worktree 下多一个 agent row，row 主文案直接是 Task 标题；Dashboard 的 Working 桶 +1。

主管看到

  • HippoTeam：team list 返回 name / role / status / pending_task_count / last_pty_line（snake_case，spec §3.3 契约）。注意 last_pty_line 被明令"不是汇报"——它只是终端最后一行噪声，正式汇报只认 stdin 注入的那两种信封。
  • Orca：dispatch-show / task-list --ready --brief / worker-list --include-remote，每行带 projection.attention 与 projection.nextAction（可直接执行的 argv）。

worker 看到

  • 两边一样：一段被粘进终端的派单正文，末尾带强制汇报语法。HippoTeam 额外把 PM 文档共维护要求 一起塞进去（要求 worker 自己维护 plan / ADR / reports+research 双产出）。

② 汇报回流：push vs pull（本次对比的核心）

HippoTeam 的 push 链路（会被打断的具体机制）

worker: team report "<result>" --dispatch <id>
  └─ team-operations.ts:1202 reportTask
       ├─ 事务：dispatch → reported + report_text + evidence + sequence
       ├─ 写 messages 表（worker_report）
       ├─ review_status = 'pending'（accept gate 开且在 scope 内）
       ├─ tasks.md recordDispatchDone → [x] / [~]
       ├─ mobilePushService.notifyWorkerDone（手机推送）
       └─ agentRuntime.writeReportPrompt(...)          ← 关键
            └─ buildOrchestratorReportPayload()
                 = "[Hive 系统消息：来自 @<worker> 的汇报]" + 正文 + "artifact: ..." + reminder 尾
                 └─ createPostStartInputWriter(主管的 PTY)
                      ├─ 等「baseline 之后出现新提示符 ❯ / ›」
                      ├─ claude 额外处理 busy（Working / Thinking / Compacting），最长等 120s
                      ├─ bracketed paste 整段文本（\e[200~ … \e[201~）
                      ├─ 等 "[Pasted text #N" 回执（3s 超时）
                      └─ 等 600–1500ms 后写 "\r"            ← 替老板按下了回车
危害点（file:line 可查）：注入器的就绪判断只看 PTY 输出（post-start-input-writer.ts:218 的 hasInteractivePromptReady(outputSinceBaseline)），完全没有"人是否正在输入"这个信号；随后 :117 的 writeInput(runId, '\r') 无条件提交。
于是：主管停在提示符上、老板正在打字 → 汇报正文被粘到光标处 + 回车提交 → 老板的半句话要么被吞、要么跟汇报拼成一条畸形输入发出去。
迟到报告也走同一条路：dispatch 已关时 recordLateWorkerReport + lateReportForwardedAt 去重后照样注入（team-operations.ts:1237）。

Orca 的 pull 链路

worker: worker_done --outcome succeeded --evidence "..."     →  只写 DB 行
coordinator: orca orchestration check --wait --types "worker_done,escalation,question" \
                                    --timeout-ms 900000 --json
  ├─ 返回本 Run 最老的一批 FIFO delivery（≤50 条）
  ├─ 未 --ack 则原样重放同批（不会悄悄丢）
  ├─ 空等待 / 超时 = 检查点，不是失败
  └─ 连续 3 次空等待 → 改 worker-list --include-remote，按 projection.attention / nextAction 行动
coordinator: orca orchestration check --ack <delivery_id> --wait ...   ← 只有 ack 才推进游标

在这整条链路里，主管的终端一个字节都没被写：因为主管始终在 turn 里（阻塞在 check --wait），而指针通道的门禁第一句就是"lastAgentStatus 必须是 idle 且观察到是活的"，否则直接 return。

老板看到

  • HippoTeam：主管窗口突然冒出一整块 [Hive 系统消息：…]，且已经被提交——老板来不及反应。
  • Orca：什么都不会冒出来。老板要自己看侧边栏 agent row 从"working"变绿（Done），或者直接问主管。

主管看到

  • HippoTeam：汇报以"用户消息"形态出现在自己的输入流里，被迫开始一个新回合。主管没有"我先忙完再读"的权利。
  • Orca：主管自己决定何时 check。可以先把手上一个 Task 的 worker-release 做完再拉下一批。

worker 看到

  • 两边一样：发完就结束自己的回合。差别在 HippoTeam 的 worker 会立刻触发主管动作（连带触发一串下游派单），而 Orca 的 worker 发完就静默——它不知道主管什么时候读。
这个差异的本质：HippoTeam 把"主管的回合边界"外包给了 worker；Orca 把它留给主管。 前者换来了低延迟（报告一到主管立刻处理），后者换来了不被打断 + 主管可以自主排序。 HippoTeam 已有的 ledger 字段（delivered_at / report_acknowledged_at / report_delivery_failed_at）说明这套"投递 vs 确认"模型其实已经具备，缺的只是"默认不注入"这一步。

③ 老板可见性：结构化看板 vs 实时仪表

HippoTeam 的三层可见性

  1. Topbar 徽标：Cockpit 按钮旁一个数字，是 buildAiActions 合成出的待办数（high/medium questions、ADR drafts、orphan reports、缺实施的 design milestone、未审代码、sentinel 告警）。不打开也能看到"有事等你"。
  2. Cockpit 抽屉 12 tab：plan / tasks / questions / ideas / decisions / research / reports / timeline / baseline / archive / setup / diagnostics，每 tab 有独立徽标（tasks 计数、questions = high+medium、decisions = drafts+adopted…）。这是从 .hive/ 下 10 个 Markdown 文档解析出来的，内容持久、可回溯、可 diff。
  3. 左侧 worker 卡片：三态 working / idle / stopped + 队列徽标 + 最后一行 PTY 输出（仅提示用）。

待拍板事项 = .hive/open-questions.md（编号 Q1/Q2 + 优先级 🔴/🟠/🟢），由 parseQuestionsDoc 解析进 Questions tab，老板在 tab 里直接答复，答完会反向注入主管终端唤醒它（buildOrchestratorQuestionAnsweredPayload）。
另有两条远程通道：飞书（team feishu reply）和手机 App（team mobile-reply），以及高风险动作的手机审批闸（team approve "动作描述" --risk high，等 ALLOWED/DENIED 注入才继续）。

Orca 的可见性

  • 侧边栏 agent row：每个 worktree 下面挂它当前的 agent，row 主文案直接是 Task 标题/displayName（截断 80 / 160 字符）。这是老板在 Orca 里最接近"任务面板"的东西——本质是"活的 agent 列表"，不是任务列表：worker 一结束，row 就变绿/变灰，任务本身不再有位置。
  • Agent Dashboard：Needs You / Working / Done / Idle 四桶 + 计数，Needs You 用问号图标。这是老板一眼扫"哪里需要我"的地方。
  • orca worktree ps：命令行形式，每个 worktree 一行，带 live:N / pty:yes|no / unread:yes|no 和终端内容预览。适合脚本化和快速巡检。
Orca 的空白：decision gate 和 pending question 没有任何 UI 面。 gate-create --task <id> --question "..." --options '[...]' 建出的 gate 只写进 orchestration DB 的 decision_gates 表（db/decision-gates/decision-gate-store.ts）；在 renderer 里 grep decision_gate 结果为空。 也就是说：Orca 的"待拍板"活在主管的终端 scrollback 里——老板关掉那个窗口，就只剩"问主管"这一条路。 （顺带纠正：OrchestrationPage.tsx 不是真实面板，是营销用的功能墙动画。）

主管看到

  • HippoTeam：team list 的 pending_task_count + last_pty_line；以及被注入的汇报本身。
  • Orca：worker-list --include-remote --json，每行带 projection.attention.categories（guidance / input / approval / failure / interruption / stale / unverifiable / root_completion）、requiresAction、以及可执行的 nextAction argv。

worker 看到

  • HippoTeam：自己那张卡片的状态和队列数（它看不到 Cockpit）。
  • Orca：worker 通过 check --terminal <handle> 读主管的 follow-up，通过 ask 阻塞提问、超时后留一条 durable question 用 message ID 续问。

④ 完成信号：自报为主 vs 客观状态 + 不许把"不知道"当结论

HippoTeam

  • 默认：worker 自报 team report → dispatch 变 reported，tasks.md 打 [x]（accept gate 开且在 scope 内则打 [~] 表示待审）。
  • 客观侧证（重要，是 HippoTeam 的强项）：ledger 有 report_overdue / orphaned 态；unreviewed-code-status.ts 会在"coder report 了代码改动、但 2 分钟宽限内没有 reviewer dispatch 跟上"时，在看板硬亮一条"未审"action——不依赖 PM 记性，never-silent。
  • 但"报告即完成"仍是默认路径：worker 说完成了，主管倾向于信。

Orca

  • worker worker_done --outcome succeeded|failed 会自动 settle Task 和 Dispatch，并且明令"不许再补一条 task-update --status completed"——避免自报与状态机打架。
  • "Absence never authorizes stop, abandon, retry, or release" 是写进 agent 手册的铁律：unverifiable（包括 worker-show 报 agentWait 为 null）只是"不知道"，必须继续等；只有三种正证据能授权停/放弃/重试：exited liveness、worker 自己观察到进程退出、或者一份最终回合没发 worker_done 的 transcript。
  • turn 结束条件是可枚举的：worker-list --run <run_id> --terminal-state reclaimable 必须返回空；每个已 settle 的终端必须显式 reuse / worker-retain / worker-release 三选一。
  • 状态变更都留 mutation_receipts，生命周期 8 态转移集中在 lifecycle-transition.ts，对账在 lifecycle-reconciliation.ts。
HippoTeam 可以低成本吸收的一条：把"完成"的判定从"worker 说完成了"改成"worker 说完成了 + 一个客观证据槽"。 HippoTeam 的 team report 已经有 --evidence 参数、ledger 也已经有 evidence_json 字段，只是目前没有被当作判定依据。

⑤ 隔离与并行：约定 vs 文件系统

HippoTeam：默认共享目录

一个 workspace 就是一个目录（workspace.path），所有 worker 的 PTY cwd 都指过去；worktree 分层只在 HIVE_WORKER_WORKTREES=1 时才启用（agent-runtime.ts:53-57，注释写明"默认关闭以保持向后兼容"）。写冲突靠角色约定消化：worker 不 commit，PM 审完在主树 commit。这条约定本身也写在 unreviewed-code-status.ts 的设计判定里。

代价：两个 worker 同时改同一个文件时，没有任何机制会拦住它们，只能靠老板/主管事后发现。并行度上限 = 能忍受的文件冲突数。

Orca：worktree 是一等公民

默认 --worktree current（不新开），但一旦需要隔离就是 new-child / new-top-level；还能落 SSH / WSL / 远端 Orca server。手册里一句话点明了它的默认观："A fresh worker means a fresh agent terminal, not a new Git worktree."——即"新 worker ≠ 新 worktree"，只有真的需要 checkout 或文件系统冲突时才开。

代价：worktree 多了之后，老板要面对"哪个分支改了什么"的合并问题；Orca 给了 git 的常规工具，没有替老板做集成。

老板看到

  • HippoTeam：一个目录 + 一堆 worker 卡片；改动全部堆在同一个工作区，git status 是所有 worker 的混合结果。
  • Orca：侧边栏按 worktree 分组，每组下面是它的 agent row；orca worktree ps 按 worktree 列出 live / unread / 终端预览。

主管看到

  • HippoTeam：team list 不区分目录，所有 worker 同一片土地。
  • Orca：placement 是一等参数（--worktree / --host），主管在派单时就要决定落在哪个 checkout。

worker 看到

  • HippoTeam：cwd 就是 workspace 根目录，看得见别的 worker 的改动（也是它 commit 纪律存在的原因）。
  • Orca：cwd 是自己那份 worktree，天然看不到别人。

⑥ 治理：管"结论可信" vs 管"调度没做错"

HippoTeam 的 L1 强制（这是它最不可替代的部分）

  • 角色 ACL：只有 orchestrator 能 send / list / cancel / recover / abandon / accept；worker 只有 report / status / help。worker 想派活？协议层直接拒绝。
  • 反自审铁律（三重校验）：team accept --reason 必须含 8 位以上 hex，且该 hex 必须命中本 workspace 内一条 reviewer 角色的 dispatch，并且：① 该 reviewer dispatch 必须真 reported；② reviewer 的 report 时间必须晚于被审 coder（同毫秒时用 sequence 严格大于来 tie-break）；③ 若 reviewer 自己设了 reviews_dispatch_id，必须等于当前这条 coder dispatch。
    代码位置：team-operations.ts:1490 起；错误信息直接写着"PM 自审反铁律：必须引用钟馗或其他 reviewer 的 dispatch_id"。
  • 未审代码兜底看板：不靠 PM 记性，见 ④。
  • sentinel 独立角色：专职巡查，走 SENTINEL_RULES，不允许承接派单汇报。
  • 高风险动作手机审批：来自飞书/手机的指令触发 rm / git push / drop table 等动作前，必须先 team approve --risk high 并等注入的 ALLOWED/DENIED。
  • PM 文档共维护：调研类工作强制 reports/*.html + research/*.md 双产出，写进 worker 的派单提示词和 worker 规则里（不是靠事后补）。

Orca 的等价物：有纪律，但没有 review 强制

  • 有：生命周期状态机 + mutation_receipts + 对账；worker-start 失败不许 relaunch，必须读 receipt 的 failedStage / residualResources；"review-only 的 worker_done 只授权综合，不授权 coordinator 改文件"；nested worker 深度上限。
  • 没有：任何"必须由第二个 agent 审过才能标记完成"的机制。worker_done 一发就 settle，没有 accept gate、没有 reviewer 角色、没有未审代码看板。"这行代码谁审过"在 Orca 里没有任何记录。

老板看到 / 主管看到 / worker 看到

  • HippoTeam 老板：Cockpit 的"未审代码"和"待确认 ADR"action 会硬亮；accept 被拒时能看到明确的 CLI 错误。
  • HippoTeam 主管：team accept 可能因为引用不出 reviewer dispatch 而被直接拒——它不能糊弄过去。
  • Orca 老板/主管：没有任何审查相关的强制或提示；是否 review 完全靠主管自律与老板追问。

五、最该借鉴的 3 件事（Orca → HippoTeam）

1. 汇报默认不注入，改成"落库 + 主管拉"

把 writeReportPrompt 从 reportTask 的默认路径里摘掉，只保留 ledger 落库 + tasks.md + 手机 push + Cockpit 徽标。主管在自己的回合边界上主动拉。

为什么值得做：现在的注入会在老板打字时替老板按回车，这是"系统对老板失礼"，也是 HippoTeam 最大的体感扣分项。decisions/draft-2026-09-19-worker-report-pull-not-push.md 已经拍了这个方向。

已有地基：ledger 已有 delivered_at / report_acknowledged_at / report_delivery_failed_at；writeReportPrompt 已支持 onPasteAck / onPasteGaveUp 回调，语义上"投递"和"确认"是分开的。

2. 给主管一个阻塞式拉取动词（check --wait 等价物）

让主管能说"我在这里等，直到有 worker_done / escalation / question"，超时是检查点不是失败；未 ack 的批次要重放而不是丢。

为什么值得做：pull 模型必须有"等"的能力，否则主管只能靠轮询，反而更吵。而且阻塞等待天然提供 liveness 信号——主管在 check --wait 里，系统就知道"它在干活，别打扰它"。

落地形态：worker 侧仍只 team report/status；主管侧加一个 team wait --types ... --timeout。注意 HippoTeam 的 worker ACL 是"只能 report/status"，新增动词必须放在 orchestrator 侧。

3. "缺席不是证据"写进 team list 输出

Orca 的 worker-list 每行直接给 projection.attention.categories + requiresAction + 可执行的 nextAction argv，并明令"unverifiable 不授权 stop / abandon / retry / release"。

为什么值得做：HippoTeam 的 team list 目前给 status + pending_task_count + last_pty_line，主管得自己推断"这个 stopped 是真退出还是只是没输出"。把 report_overdue / orphaned / delivery_failed 显式渲染成 attention 类别 + 建议动作，主管就不用靠猜。

六、最不该丢的 3 件事（HippoTeam 独有）

1. 文件化、可浏览、可回溯的治理状态

Cockpit 12 tab + Topbar 徽标 + open-questions.md / decisions/ / baseline/ / reports/+research/ 双产出。

Orca 的对应物：无。Orca 的待拍板（decision gate）和 pending question 根本没有 UI 面，只存在 DB 与终端 scrollback 里。HippoTeam 的看板是老板关掉终端之后仍然存在的东西——这是 pull 改造里最容易被顺手丢掉、但绝不能丢的部分。

2. 反自审的代码级强制（accept gate）

team accept --reason 必须引用一条真 reported、时序在后、指向正确的 reviewer dispatch，同毫秒还要 sequence tie-break。

Orca 的对应物：无。Orca 把"要不要 review"完全交给主管自觉，没有任何 L1 强制，也没有"这行代码谁审过"的记录。HippoTeam 如果为了 pull 模型去简化 accept，等于把最值钱的护栏拆了。

3. PM 文档共维护 + 跨 session 知识连续

baseline（module-map / runtime-flows / state-storage / test-gates / risk-hotspots）+ ADR + plan-vs-actual review + 调研双产出，全部写进 worker 的派单提示词里强制执行。

Orca 的对应物：无。Orca 的知识活在终端 scrollback 和 git 历史里；新 session 的 coordinator 只能重新读代码。HippoTeam 的 baseline 是"跨 session 不重新 grep"的答案。

八、盲区与未验证项

  • Orca 的"人在打字"检测：确认不存在。在 src/main 与 src/shared 里 grep userTyping / isTyping / localInput 只命中无关模块。所以 Orca 也没有解决"老板正在打字"这件事——它只是把触发窗口压窄了（idle 门禁 + 只写一行指针 + 主管通常都在 turn 里）。不要把它当成"已经解决了打扰问题"。
  • Orca 的 human-facing 交互没有实测：本次只读了代码与 agent 手册，没有在 GUI 里手动跑一遍"worker_done 后侧边栏 row 如何变化"、"Needs You 桶什么时候亮"。四桶计数与 row 主文案的结论来自代码，未做端到端目视确认。
  • Orca 的 cloud/（474 个文件）仍未读，沿用 2026-09-14 审计的同一盲区。若那边有老板侧的任务/审批 UI，本文的 ③ 结论需要修订。
  • Orca 的 decision gate 生命周期只读到 DB 层（create / resolve / timeout / list），没有确认"gate 是不是设计给人类拍的"。手册原文是"Use a gate only for a coordinator-owned Task-DAG decision"，倾向于 gate 是主管自己的 DAG 决策记忆，而非老板待办——但这一点没有反证。
  • HippoTeam 侧只做了静态阅读，没有起服务实测注入打断。危害路径（粘贴 + 自动回车顶掉老板输入）是从 post-start-input-writer.ts 的控制流推出的，未做"老板打字中触发 report"的实机复现。
